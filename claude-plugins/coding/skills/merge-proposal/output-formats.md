# 提案ファイルの書式

3ファイルとも `merge_report.py` の出力ディレクトリ(`CONFLICTS.md` / `INCOMING.md` と同じ場所)に書く。冒頭には共通で次のヘッダを置く。

```markdown
# <提案の種類>: <取り込むブランチ> -> <現在のブランチ>

- 現在のブランチ: <branch> (<sha>) / 取り込むブランチ: <branch> (<sha>) / merge-base: <sha>
- 入力: CONFLICTS.md / INCOMING.md
- 注意: <未コミット変更がある、他の提案ファイルを作っていない、等。無ければ行ごと省く>
```

提案は「そのまま適用できる具体性」で書く。コード片は解消後・修正後の全体を載せ、差分だけで済む場合は unified diff で書く。

## 1-conflict-resolution.md(コンフリクト解消案)

コンフリクトが0件なら、ヘッダの後に「コンフリクトはありません。」とだけ書く。

````markdown
## サマリ

| #   | path        | 種別          | 方針                   | 要確認 |
| --- | ----------- | ------------- | ---------------------- | ------ |
| 1   | src/calc.py | content       | 両方を統合             |        |
| 2   | config.txt  | modify/delete | 削除を採用し設定を移す | ●      |

## 1. src/calc.py

### ハンク 1 (L5-L11)

- 現在のブランチの意図: <何のための変更か>
- 取り込み側の意図: <何のための変更か。コミットメッセージや周辺差分から読む>
- 方針: 現在を採用 / 取り込みを採用 / 両方を統合 / 書き直し

解消後:

```python
<マーカーを除いた、解消後のコード>
```

理由: <なぜこの形か。捨てる側があれば、失われる挙動>
````

- `modify/delete`・`rename/delete` などマーカーの無い種別は、ハンクの代わりに「残す版・消す版」と、消える側の変更を別の場所へ移す必要があるかを書く。
- 意図が読み取れず判断できないものは方針を決めつけず、「要確認」に ● を付けて選択肢と問いを書く。

## 2-incoming-review.md(取り込み内容のレビュー・修正案)

````markdown
## 総評

<取り込み内容の概要と、取り込んでよいかの所見を2〜4行>

## 指摘

| #   | 重要度 | path:行       | 概要                  | 修正場所   |
| --- | ------ | ------------- | --------------------- | ---------- |
| 1   | high   | src/api.py:12 | None を返す経路で例外 | 取り込み元 |
| 2   | low    | docs.md:3     | 旧関数名が残っている  | 取り込み後 |

### 1. <概要>

- 問題: <何が起きるか。再現条件>
- 修正案:

```diff
<修正差分>
```
````

- 重要度は `high`(バグ・データ破壊・セキュリティ) / `medium`(既存動作への影響・テスト不足) / `low`(可読性・命名・ドキュメント)。
- 修正場所は `取り込み元`(取り込む前に元ブランチで直すべき) / `取り込み後`(現在のブランチで直せば足りる)。
- 指摘が無ければ「指摘はありません」と書き、確認した観点を1行添える。

## 3-follow-up.md(現在のブランチの追従修正案)

取り込み側の変更が、現在のブランチのコードに求める修正を書く。コンフリクト解消そのものは 1 に書き、ここでは重複させない。

````markdown
## 取り込み側で変わった前提

| #   | 変更                          | 取り込み側の該当箇所 |
| --- | ----------------------------- | -------------------- |
| A   | greet() を say_hello() に改名 | api.py               |
| B   | config.txt を廃止             | config.txt           |

## 追従修正

| #   | 前提 | path:行  | 内容                                 | 放置した場合 |
| --- | ---- | -------- | ------------------------------------ | ------------ |
| 1   | A    | app.py:1 | import と呼び出しを say_hello に変更 | ImportError  |

### 1. app.py

```diff
<修正差分>
```

## 確認が必要なこと

- <テストの再実行、生成物の再生成、判断が要る点など>
````

- 「前提」は API・関数/クラス名・引数・戻り値・設定キー・ファイル配置・スキーマ・依存バージョン・規約の変更を拾う。
- 影響箇所は、現在のブランチ側の変更ファイルに加えて、現在のブランチ全体を検索して探す(`git grep <旧名> <現在のブランチ>`)。現在のブランチで新しく書いたコードが、取り込み側の変更前の前提に依存しているケースが本命。
- 1 を作っていない場合でも、コンフリクトのあるファイルに追従修正が要るなら、その旨と前提をここに書く。
- 追従修正が無ければ「追従修正はありません」と書き、確認した前提の一覧は残す。
