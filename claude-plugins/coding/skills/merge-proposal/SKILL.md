現在のブランチ(取り込み先)に `$incoming` を取り込むと仮定して、マージの**提案**を作る。

**やらないこと:** `merge`/`rebase`/`checkout`/`commit`/`push`/`stash`/`add`/`reset` など、ブランチ・インデックス・作業ツリーを変える git 操作。リポジトリ内のソースファイルの編集(提案の適用)。提案後のマージ作業の進め方の指示。書き込むのはスクリプトの出力ディレクトリ(`temp/merge/` 配下)だけ。

## 1. 取り込むブランチと実施項目を確定する

- **取り込むブランチ**: `$incoming`。無ければユーザーに確認する(推測しない)。取り込み先は現在のブランチ。別ブランチを取り込み先にしたいと言われたら `--current <branch>` を使う。
- **実施項目**: 次の3つから、ユーザーの指定に従って絞る。指定が無ければ全て行う。

  | 項目                                    | 出力ファイル               | 読む入力                               |
  | --------------------------------------- | -------------------------- | -------------------------------------- |
  | `conflicts` コンフリクト解消案          | `1-conflict-resolution.md` | `CONFLICTS.md`                         |
  | `review` 取り込み内容のレビュー・修正案 | `2-incoming-review.md`     | `INCOMING.md`                          |
  | `followup` 現在のブランチの追従修正案   | `3-follow-up.md`           | `INCOMING.md`(+現在のブランチのコード) |

  「コンフリクトだけ」「レビューは要らない」のような自然文も、この3項目に読み替える。指定されなかった項目のファイルは作らない。

## 2. レポートを生成する

```
python ${CLAUDE_SKILL_DIR}/merge_report.py <incoming> [--current <branch>] [--repo <path>] [--output-dir <dir>]
```

`temp/merge/{unixtime}_{hash}/` に次の2ファイルが出る。標準出力はパスと件数だけ。

- `CONFLICTS.md` — コンフリクトファイルごとに、種別(content / modify/delete / rename/delete 等)、両側の変更(merge-base からの diff)、コンフリクト箇所(zdiff3 形式のマーカー、マージ結果ファイルの行番号付き)
- `INCOMING.md` — 取り込まれるコミット一覧、現在のブランチ側の変更ファイル一覧、取り込み側の変更ファイルごとの diff。各ファイルに「両側変更」「コンフリクト」のフラグ

両ファイルとも冒頭のサマリ表に各セクションの開始行がある。大きいときはサマリ表だけ読み、Read の `offset` で必要なセクションを読む。

終了メッセージの扱い:

- 「取り込む内容はありません」(同一コミット・取り込み済み) → その旨を伝えて終了する
- エラー(ブランチが無い・共通祖先が無い・git が古い) → 内容をそのままユーザーに伝えて終了する
- 「作業ツリーに未コミット変更があります」 → 提案はコミット済みの状態が対象であることを報告に書く

## 3. 提案ファイルを書く

実施項目ごとに、同じ出力ディレクトリへ提案ファイルを書く。書式と観点は `${CLAUDE_SKILL_DIR}/output-formats.md` に従う。要点:

- **コンフリクト解消案**: ハンクごとに、両側の意図 → 解消後のコード → 理由。どちらかを捨てる場合は何を失うかを書く。
- **取り込み内容のレビュー**: 通常のコードレビューの観点(バグ・既存動作への影響・テスト)で指摘し、修正案を付ける。修正を取り込み元で直すべきか、取り込み後に現在のブランチで直すべきかを分ける。
- **追従修正案**: 取り込み側で変わった API・関数名・設定・スキーマ・前提を洗い出し、現在のブランチ側の変更ファイル(と現在のブランチ全体)で影響を受ける箇所を探す。コンフリクトにならずに自動マージされる「両側変更」ファイルと、現在のブランチで新しく追加した呼び出し元は特に見る。
  - 現在のブランチのコードは、作業ツリーが取り込み先ブランチと同じならファイルを直接読み、そうでなければ `git show <branch>:<path>` / `git grep <pattern> <branch>` で読む。

読み取りのための git コマンド(`diff`/`show`/`log`/`grep`/`blame`)は使ってよい。

## 4. 報告する

次を簡潔に報告する。提案の本文はファイルにあるので、チャットに全文を貼らない。

- 取り込み元・取り込み先・コンフリクト件数・取り込みコミット数
- 書いた提案ファイルのパスと、各ファイルの要点(重大な指摘は1〜3件だけ抜き出す)
- 実施しなかった項目があればその旨
- git の状態を変える操作・ソースファイルの編集は行っていないこと
