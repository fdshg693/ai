# 実装フロー提案

このスキル自体は調査も提案もしない。呼び出したあなた（メインエージェント）が、以下の手順でflow-proposerサブエージェントを呼び出し、その回答をそのままフロー提案として使う。

## 手順

1. **実装依頼の内容を確定する**
   - `$ARGUMENTS`が実装依頼の全文であればそれを使う
   - 空の場合は、直近の会話でユーザーから受けた実装依頼を自分で特定する。それでも特定できなければ、それ以上進めず「実装依頼の内容が不明なため提案できない」とだけ返して終了する

2. **自分が既に把握している理解を棚卸しする**
   - ここまでの会話で既に読んだファイル、既に把握した制約・ルール・既存構造、既に決めた方針、着手前に判明した懸念点などを短く箇条書きにする
   - まだ何も調査していない依頼であればこの項目は空でよい（無理に埋めない）

3. **Agent toolでflow-proposerサブエージェントを呼び出す**
   - `subagent_type: flow-proposer`を指定する
   - プロンプトには次の2つを含める（このスキル自身が調査・判定を行うのではなく、これらをそのまま渡すだけ）

     ```markdown
     ## 実装依頼

     <手順1で確定した依頼の全文>

     ## 呼び出し時点で分かっていること（あれば）

     - <手順2で棚卸しした内容>
     ```

     「分かっていること」が無ければその見出し自体を省略してよい

   - 結果をすぐ使いたいので、フォアグラウンドで呼び出す（`run_in_background: false`）

4. **結果をそのまま使う**
   - flow-proposerから返ってきたMarkdown（調査ステップ／実装ステップ／テストステップ）を、自分の言葉で要約し直したり内容を変えたりせず、そのままフロー提案として提示する
   - このスキルの役割はここまでで終わり。実際の調査・実装・テストの実行方針は、提案を見た上で呼び出し元（ユーザーまたは自分自身）が決める
