## Anthropic 固有フィールドの扱い

ゲートウェイは Anthropic Messages 形式を受け取り、OpenAI 形式（Responses API 等）へ**変換**する。「受理された」ことと「上流で同じ機能が働いた」ことは別物なので、混同しない。

| フィールド                     | 実際に起きること                                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `tools` / `tool_choice`        | Anthropic 形式の `tool_use` ブロックとして往復する。ツールループは成立する                                   |
| ストリーミング（SSE）          | `message_start` 〜 `message_stop` のイベント列として返る。バッファされず逐次届く必要がある                   |
| `cache_control`                | Messages 境界では受理されるが、上流形式へ変換される。**OpenAI 側のプロンプトキャッシュが効いた証拠ではない** |
| `anthropic-beta` ヘッダ        | ゲートウェイまでは到達する。上流でどう解釈されるかは別問題                                                   |
| `context_management`（クリア） | 受理される。入力が閾値未満なら何も起きない（`applied_edits` が返らない）。受理＝動作確認ではない             |
| `context_management`（圧縮）   | ゲートウェイ側に要約用モデルの設定が必要。未設定だと実行されず、成功したように見える                         |

**確認の原則**: 200 が返ったことを機能の証拠にしない。ゲートウェイの詳細デバッグログで、上流へ何が送られたか（変換された形跡か、意図的な非対応か）を見る。

**リバースプロキシを挟む場合**は、クエリ文字列（`?beta=true`）、`anthropic-version`、`anthropic-beta` を落とさないこと。SSE をバッファしないこと。

## 無害な診断・紛らわしい失敗

これらは構成の失敗ではない。追いかけない。

- **カスタムモデル ID に対する `unrecognized_model` 診断** — Claude Code が知らない ID に対して出す。API リクエスト自体は成功している。`modelUsage` とゲートウェイのログで判断する。
- **モデルピッカーに OpenAI モデルが出ない** — ゲートウェイのモデル探索は ID に `claude` / `anthropic` を含むものだけをピッカーへ追加する。明示指定で動けば正常。
- **Remote Control 等が使えない** — カスタム base URL では一部機能が無効になる仕様。
- **テレメトリ（OTLP）の connection refused** — 親プロセスから `CLAUDE_CODE_ENABLE_TELEMETRY` を継承していると、送信先が無いログが出る。モデル接続とは無関係。

## 切り分け手順

下の層から順に確認する。飛ばさない。

1. **上流プロバイダ直叩き** — そのモデル ID・そのキーで OpenAI API が 200 を返すか。失敗するならゲートウェイ以前の問題。
2. **ゲートウェイ単体** — `curl` で `POST /v1/messages`。基本応答 → SSE → 強制 `tool_choice` の順。前段が落ちたら後段を試さない。
3. **Claude Code E2E** — 隔離した非対話実行（下記）。
4. **フィールドの特定** — 400 が出たら、エラー本文と変換ログを保存してから、疑わしいフィールド（`thinking`、tool schema、`anthropic-beta`、`context_management`）を **1つだけ** 外した raw リクエストを送る。`drop_params: true` を先に入れると原因が見えなくなる。

ログに対して `context_management|drop_params|summary_model|tool|stream|400|401` を grep すると、棄却・破棄・変換された箇所が出る。ログを貼り出す前に認証情報を除去する。

## 隔離環境での検証

自分の設定・プラグイン・フックの影響を排除して確認したいとき:

- 空の一時ディレクトリを `CLAUDE_CONFIG_DIR` に指定する。**これだけではプロジェクトの settings/hooks は残る。**
- `--safe-mode` を併用する（カスタム hooks / MCP / skills を無効化）。それでも managed policy は残り得るので、完全分離とは言わない。
- cwd をリポジトリ外の新規ディレクトリにする。
- `--no-session-persistence` と `--debug-file` を付ける。
- `--bare` は**使わない**。認証が API キー / `apiKeyHelper` に限定され、`ANTHROPIC_AUTH_TOKEN` の Bearer 経路を検証できない。

詳細は **claude-code-debugging スキル**（`testing.md`）を参照。

## 症状別の対処

| 症状                       | 見るところ                                                                                                                                          |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 401 / 認証エラー           | `ANTHROPIC_AUTH_TOKEN` と `ANTHROPIC_API_KEY` が併存していないか。ゲートウェイが `x-api-key` のみ受ける構成なら、どちらか一方に統一して対照実験する |
| モデルが見つからない / 404 | `--model` の文字列とゲートウェイの `model_name` が完全一致しているか。省略して既定の Claude ID が送られていないか                                   |
| 応答は返るが Claude っぽい | `modelUsage` とゲートウェイのログを突き合わせる。base URL が効いていない可能性                                                                      |
| 400（特定リクエストだけ）  | 上記「フィールドの特定」。フィールドを1つずつ外す                                                                                                   |
| ストリーミングが一括で届く | 間のリバースプロキシが SSE をバッファしていないか                                                                                                   |
| ツールを呼ばない           | 変換失敗とは限らない。モデルが選ばなかっただけの可能性。`tool_choice` を強制した raw リクエストで切り分ける                                         |
| 接続拒否                   | ゲートウェイのプロセス／コンテナが生きているか。ポートが loopback バインドで、同じホストから叩いているか                                            |
