# 見やすさ・メンテしやすさのテクニック

文法的に正しいMermaidコードでも、書き方次第で「線が交差して読めない」「文字が小さくて潰れる」「変更のたびに全ノードのIDを書き換える」ことになる。ここでは症状別に対処法をまとめる。

## 線が交差する・読みにくい

- **`direction`を疑う** — 横に広い/階層が深いグラフは`flowchart LR`（左右）、手順を上から順に追わせたい図は`flowchart TD`（上下）が基本的に交差が少ない。交差がひどいときは、まず方向を変えて比較する。

  ```mermaid
  flowchart LR
      A[Client] --> B[API Gateway] --> C[Service]
  ```

- **不要なエッジを足さない** — `A --> B --> C`が既に成立しているなら、`A --> C`を「暗黙に含まれる関係」として重ねて足さない。意味的に異なる関係（例: Cへの直接アクセスも別経路として実在する）でない限り、エッジ1本増えるごとに交差の可能性が増える。
- **`subgraph`は「意味のあるまとまり」にだけ使う** — レイアウトをごまかす目的で節操なく`subgraph`を増やすと、ネストが深くなるほどレイアウト計算が複雑になり、かえって交差・崩れが増える。

  ```mermaid
  flowchart LR
      subgraph Frontend
          UI[Web UI]
      end
      subgraph Backend
          API[API Server]
          DB[(Database)]
      end
      UI --> API --> DB
  ```

- **ノード数が多い（目安20を超える）なら1枚に収めようとしない** — レイヤー単位・モジュール単位で図を分割する。「全体を1枚で見せる」より「今説明したい部分だけを見せる」方が、読み手が構造を組み立て直す負担が小さい。

## 文字が小さく見える・潰れる

- **ラベルは短く** — ノード内のテキストは単語かごく短いフレーズに留め、長い説明はMermaidの外（周囲のMarkdown本文やArtifactのキャプション）に書く。ノード内に文章を詰め込むほど、レンダラーがノードを拡大するかフォントを縮小するかで表示が崩れやすくなる。
- **矢印には意味のあるラベルを付ける** — ラベルなしの矢印は「何か関係がある」としか言っていない。`-->|writes|`・`-->|invalidates|`・`-->|polls every 30s|`のように、関係の種類が名前だけで分からない場合はラベルを付ける。逆に自明な関係（`A --> B`が単純な処理の流れ）にまで律儀にラベルを付けると、かえって図がうるさくなる。

  ```mermaid
  sequenceDiagram
      participant Client
      participant Cache
      participant DB
      Client->>Cache: read(key)
      Cache-->>DB: miss: fetch
      DB-->>Cache: value
      Cache-->>Client: value
  ```

## メンテしにくい（直すたびに全体を書き換える羽目になる）

- **ノードIDと表示ラベルを分ける** — `svc[Order Service]`のように、短く安定したID（`svc`）と人間向けの表示テキスト（`Order Service`）を分離する。表示名を変えたいだけならラベルの中身だけ直せばよく、他のノードから伸びているエッジ（`svc --> db`のような行）を一切触らずに済む。IDに日本語や空白を使わない。
- **`%% comment`で「なぜ」を書く** — なぜこのエッジを意図的に描いていないか、なぜこの構成にしたか等、図だけでは伝わらない非自明な判断はコメントで残す。コードのコメントと同じ基準（自明なことは書かない、次に読む人が驚く点だけ書く）。

  ```mermaid
  flowchart TD
      %% Legacy path (v2) is intentionally omitted here — see ADR-042
      A[Request] --> B[New Handler]
  ```

- **色・スタイルは意味を持たせる要素だけに絞る** — `classDef`で全ノードを色分けすると、結局「何が重要か」が伝わらなくなる。比較で選ばれた方、ボトルネックになっている箇所など、主張したい1〜2箇所だけに色を使う。

  ```mermaid
  flowchart LR
      A[Old Path] --> C[Shared Service]
      B[New Path] --> C
      class B highlight
      classDef highlight fill:#f96,stroke:#333,stroke-width:2px
  ```

## 比較・状態遷移を描くとき

- **選択肢を並べるだけの図は比較にならない** — 「オプションA」「オプションB」を別々の箱として並べただけで、両者をつなぐ矢印も差分もなければ、それは選択肢の箇条書きを図にしただけで比較にならない。何が変わるのか（増える/減るエッジ、置き換わるコンポーネント）を実際に描く。
- **状態遷移図は全状態を書き出す前に「意思決定に関係する遷移」を洗い出す** — 些末な内部状態まで律儀に書くと`stateDiagram-v2`は簡単に交差だらけになる。読み手の意思決定に関わる遷移だけを残す。
