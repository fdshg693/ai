# repo-wide/ — このリポジトリ自身のメンテナンス概念

このリポジトリ自身のメンテナンスに関する概念ドキュメント群。もとは `meta-plugins/skills/` 配下のメタスキルとして分散していたが、二重管理を避け関連ファイル同士の関係を明示的なリンクで見えるようにするため、OKF概念ドキュメントへ移行した。ルーティングは `meta-plugins/skills/meta/` スキルが担う。

- [aim-automation](aim-automation.md) — Explains this repository's preference for automating repetitive, judgment-light text tasks (summarizing files, batch-answering the same question across many files, filling in SKILL.md metadata) with the lightweight tools/aim family (aim, aim-summarize) instead of a full AI coding tool session, and when fanning a prompt out across many paths in parallel is the right lever. Use when a task is "run the same simple prompt over N files/dirs" or "pick a model tier for a one-shot text task" and a full agentic session would be overkill.
- [ai-tools-config](ai-tools-config.md) — Explains how this repository's AI-tool plugin/marketplace/skill-catalog files (marketplace.json, skill-catalog.json, CATALOG.md, Cline rules, Copilot instructions, README's tool section) are generated from ai-tools.yaml and regenerated. Use when adding/removing a Claude/Codex/Copilot/Cline plugin, when a generated file (marked "DO NOT EDIT MANUALLY") looks stale or wrong, or when asked how this repo's marketplace/catalog files are kept in sync.
- [claude-code-first-skills](claude-code-first-skills.md) — Explains this repository's policy that most SKILL.md content is written for Claude Code specifically (exploiting its frontmatter mechanisms like allowed-tools, disable-model-invocation, dynamic `!command` context injection, and this repo's own meta block) and only appears for another AI tool as a meta-skill about using that tool itself, not a ported copy. Use when deciding whether a skill belongs under claude-plugins/meta or a specialized claude-plugins/ plugin only, whether to port an existing Claude Code skill to cline-plugins/codex-plugins/copilot-plugins/cursor-plugins, or why those folders look sparser than claude-plugins.
- [gh-actions-lifecycle](gh-actions-lifecycle.md) — Explains how this repository's release/deploy and issue/PR automation entirely run on GitHub Actions under .github/workflows/ — the skills-site build-verify-deploy-tag pipeline to Azure Static Web Apps, the gh-aw agentic workflows (Markdown source compiled to *.lock.yml, plus the auto-generated maintenance workflow), and the Claude/Codex/PR-Agent issue and PR bots. Use when a GitHub Actions run fails, when asked how a deploy/release actually happens in this repo, when adding or editing anything under .github/workflows/, or when deciding which secret a given workflow needs.
- [hook-distribution](hook-distribution.md) — Explains how this repository's AI-agent hooks flow from a single source (agent-tooling hook scenarios with per-hook hook.yaml) through a build that aggregates generated/catalog.json, to distribution by `skill-tools hooks` via the root repo-hooks.yaml, and how this repository self-installs its own hooks with `just hooks-install` instead of the retired hooks_manager. Use when adding or changing a hook, when .claude/hooks or a settings.json hooks entry looks stale, or when another project wants to install hooks from this repo.
- [justfile-conventions](justfile-conventions.md) — Explains how justfiles are structured across this repo (root + per-tool, each with `set windows-shell`, a `default` recipe that runs `@just --list`, and a leading cwd comment) and the convention of routing recipes through mise-managed tool versions so they resolve identically regardless of which shell/GUI process launched them. Use when adding or editing a justfile recipe, deciding whether a new justfile is warranted, or a recipe behaves differently across shells/terminals.
- [lefthook-automation](lefthook-automation.md) — Explains this repository's policy of pushing as much repo-hygiene enforcement as possible into lefthook's pre-commit jobs (regenerating derived files, backfilling SKILL.md defaults, formatting Markdown/Python, blocking on missing meta.version bumps) instead of relying on contributors or agents to remember manual steps. Use when adding a new kind of generated/derived file, a new formatter, or deciding whether a repo-hygiene check belongs in lefthook versus a skill's instructions.
- [repo-ssot-pattern](repo-ssot-pattern.md) — Explains this repository's habit of designating one explicitly-edited file as the single source of truth for a cross-cutting concern (which AI-tool plugins exist, what a SKILL.md meta field means) and regenerating every derived file from it via a script, rather than letting the same fact live in multiple hand-maintained places. Use when introducing a new fact that needs to stay consistent across several files, wondering which file is authoritative when two disagree, or deciding whether to hand-edit a file marked "DO NOT EDIT MANUALLY".
- [repo-tools-config](repo-tools-config.md) — Explains how repo-tools.yaml registers which tools/-rooted CLI tools a SKILL.md may declare as an install-time prerequisite (meta.requires_repo_tools / meta.requires_install), and which other registered tools each entry depends on (requires_tools), how check_skill_repo_tools.py and check_repo_tool_relations.py enforce it at commit time, and how skills-site's repo-tools-registry.mjs consumes the same file to render its public tool list. Use when adding a new tools/ CLI that a skill or another tool depends on, when a lefthook "repo-tools consistency" check fails, or when deciding whether a tool needs registering here at all.
- [skill-improving-meta-skills](skill-improving-meta-skills.md) — Explains how to decide whether new repo-maintenance guidance belongs as a new concept doc under docs/repo-wide/, should be integrated into an existing doc, or warrants keeping/extending the meta skill (meta-plugins/skills/meta/) that routes to these docs. Use when adding maintenance knowledge about this repository and unsure where it should live.
- [skill-md-commits](skill-md-commits.md) — Explains what this repository's lefthook pre-commit hook does whenever a commit touches any SKILL.md (regenerating skill-catalog.json/CATALOG.md, backfilling meta.version/meta.description defaults, blocking on a missing meta.version bump), and how to get such a commit through cleanly. Use when a commit touching SKILL.md files fails in lefthook, when the pre-commit hook produces a much larger diff than expected, or when asked how to bump meta.version across many skills at once.
- [skill-meta-fields](skill-meta-fields.md) — Maintains the meta fields in this repository's SKILL.md frontmatter by using an aim script to inspect skill directories and fill missing values. Use when a skill is added or its dependencies, hooks, installation requirements, environment requirements, or repository-tool usage changes.
- [skill-tools-contract](skill-tools-contract.md) — Explains that tools/skill-tools is the CLI that makes this whole repository searchable and loadable as a skill/tool catalog, and which repo files and item conventions it reads as its input contract (ai-tools.yaml plugin roots, SKILL.md frontmatter, skills-site/site-overrides.yaml, repo-tools.yaml, repo-workflows.yaml, repo-hooks.yaml hook catalog, bundle copy policy). Use when adding/moving a plugin, skill, tools/ CLI, workflow, or hook and wanting it to show up in skill-tools, or when skill-tools fails with a catalog error.
- [skill-tool-relations](skill-tool-relations.md) — Defines the directed graph of skills and tools so that changing either has an obvious blast radius — skills declare related skills/tools via meta_field.yaml fields, tools reverse-lookup consuming skills, and tool-to-tool edges are declared as requires_tools on repo-tools.yaml. Use when adding or changing a skill or a tools/ CLI and unsure which related skills/tools to update, or when deciding how tool-to-tool dependencies should be recorded.
- [tool-companion-skills](tool-companion-skills.md) — Explains the repository's pattern of pairing a tools/ convenience script with a SKILL.md that documents just its non-obvious usage decisions (e.g. claude-plugins/my-tools/skills/aim-cli for the `aim` CLI), so a human or agent isn't left guessing which flag/model/enum value to pick, and how usage feedback is stored with `skill-tools --fb` (one file per note under a configured fb root, gitignored) instead of a per-tool `--fb` flag. Use when adding a new tool under tools/ and deciding whether it needs a companion skill, when writing one, or when recording usage feedback about a skill, tool, or workflow.
- [tool-conventions](tool-conventions.md) — Explains this repository's shared rules for first-class CLI tools and scripts: process-env precedence, layered TOML config (project file up to the git root, then global user config) for installable CLIs with path or per-project settings, fixed-path .env for other scripts, path-aware missing-key diagnostics, manifest version as the SSOT, auto patch bumps for repo-tools.yaml registered tools, and one-line side-effect-free `--version` support on every public CLI entrypoint. Use when adding or editing a tool/script, exposing a new CLI command, deciding where a tool reads its settings, or deciding how a tool's version should be stored and bumped.
- [tools-directory-layout](tools-directory-layout.md) — Explains the directory conventions this repo uses for convenience scripts under tools/ — one directory per tool (or a grouping subfolder for related tools, e.g. tools/aim-use/), its own README/AGENTS.md/CLAUDE.md import chain, and turning it into a globally installable CLI via a pyproject.toml console_scripts entry. Use when adding a new script/tool to tools/, deciding whether it needs its own subfolder or a real package, or wiring up its CLAUDE.md.
- [uv-workspace](uv-workspace.md) — Explains how this repository manages its scattered Python packages (under tools/, tools/aim-use/, claude-plugins/*/skills/, integrations/) as one uv virtual workspace defined by the root pyproject.toml, including global CLI installs vs the shared dev venv. Use when adding a new Python package to the repo, wondering why `uv sync`/`uv run pytest` don't see a package, or deciding whether a directory needs its own pyproject.toml at all.
