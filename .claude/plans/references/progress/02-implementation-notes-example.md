# Step2 実装: 実装メモ・計画との差分（サンプル）

> [../02-implementation-step-example.md](../02-implementation-step-example.md) の実行で生じた「計画通りにいかなかった差分」と「実装中のその場の判断」をまとめた progress ファイルのサンプル。実装対象ではありません。

## このファイルの位置づけ

Step2の実装中、プランファイル本体の決定事項・落とし穴節だけでは収まらない詳細が生じたため、ここに分離した。プランファイル本体には「実行中に判明した変更」節として1〜2行のサマリ + このファイルへのリンクを残してある。後続ステップまたは後続タスクがあれば、そのプラン本文を直接更新する。

## 計画との差分

### 差分1: APIのエラーレスポンス構造が想定と異なっていた

プラン（[../02-implementation-step-example.md](../02-implementation-step-example.md)）では zipcloud は「該当なし = HTTP 200 + `results: null`」と想定していた。実装中に実際にエンドポイントを叩いて確認したところ、**zipcloud側のサーバエラー時も HTTP 200 のまま `message` フィールドにエラー文言が入る**ことが分かった（Step1の調査では該当なしパターンしか確認しており、サーバエラーパターンを読み落としていた）。

対応:

- `PostalCodeApiClient` では `results == null` だけでなく `message != null` もエラー扱いとする
- この変更はプランの決定事項表の1行を修正する程度で済んだため、プランファイル本体の「計画との差分」節に1行で残し、理由の詳細はこのファイルに書いた
- ルールファイル（`external-api.md` / AGENTS.md 等、レポジトリのルール格納先）にも「`message` フィールドの有無でもエラーを判定する」を追記した

### 差分2: DI登録箇所の変更

プランでは `AccountController.cs` のDI登録を想定していたが、実装時に本プロジェクトのDI登録は `Program.cs` に集約されていることを発見（「読むべきファイル」の優先度:中で `AccountController.cs` を読んだ際に判明）。DI登録は `Program.cs` 側へ移動した。触るファイル一覧は本体側で更新済み。

## 実装中のその場の判断（プランに書かなかったもの）

- `PostalCodeApiClient` の戻り値を `Result<AddressDto?>`（成功/該当なし/エラーの3値）で包んだ。プランでは「204相当を返す」としか書いておらず、戻り値の型は実装時に既存の `ArticleService` の戻り値パターンに合わせて決めた
- JS側の郵便番号入力のデバウンスは 300ms にした。プランに記載なし。既存の検索入力欄のデバウンス値を踏襲

これらは「実装時に既存の類似ファイルを読んで導出すればよい」もの（[../README.md](../README.md) の方針どおり）なので、プランに書かなかった。progress には「何を踏襲したか」だけ残し、コード本文は書かない。

## 完了記録

この機能の実装はStep2で完了。後続タスクが新たに作られる場合は、その対象プランにスコープと前提を直接記載し、このファイルを引継ぎ先にはしない。

- **完了範囲**: `PostalCodeApiClient`、フォームの住所自動入力、外部API呼び出し規約を追加した。
- **検証結果**: 該当あり、該当なし、APIエラーの各レスポンスを確認し、住所入力とエラー処理が期待どおりであることを検証した。
- **計画との差分**: zipcloudの`message`判定とDI登録箇所の2点をプラン本文へ反映済み。詳細は上記「計画との差分」を参照。

## 書き方のポイント

- **「計画との差分」はプランファイル本体に1〜2行のサマリ + progress へのリンク、progress に理由の詳細を置く。** 差分の理由を本体に長く書くと、本来の決定事項表と混ざって「計画時点の決定」と「実行時の変更」の区別がつかなくなるため。
- **progress には「何を変更したか」だけでなく「なぜ気づけたか（どのタイミングで判明したか）」も1行残す。** 上記差分1は「実装中に実際にエンドポイントを叩いて確認したとき」に判明した、と書いてある。次に同種の見落としを防ぐための手がかりになる。
- **実装中のその場の判断は「既存の何を踏襲したか」だけ書く。** コード本文はプランと同様progressにも書かない。判断の根拠となった既存ファイル名を残す程度で十分。
- **後続タスクへの引継ぎは、対象プランを直接更新する。** progressには詳細な経緯を残してよいが、次に何をするかをここだけに書かない。対象プランがまだ無い将来候補は、後続タスクを作成するときにそのプランへ記載する。
