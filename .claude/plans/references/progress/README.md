# progress/ — プラン実行中の進捗・詳細記録（サンプル）

> `.claude/plans/references/progress/` 配下のサンプル。プラン実行中に生じた「詳細な調査結果・実装メモ・計画との差分の理由」を、メインのプランファイル（`references/` 直下のファイル）とは別にまとめる場所の書き方を示す。実装対象ではありません。後続ステップ・後続タスクへの作業指示はここではなく、対象プランを直接更新する。

## なぜ progress フォルダを分けるか

プランファイル（`00-overview.md` / `01-*.md` / …）は、実装者が「次に何をすればよいか」を一目で把握するための**目次・導線**として保ちたい。実行が進むたびに調査の生ログ・実装の細かい判断・差分の理由をプランファイル本体へ追記していくと、スキャン性が落ち、本来の「やること・触るファイル・決定事項」が埋もれてしまう。

だから:

- **プランファイル本体（`references/` 直下、実際のプランでは `<機能名>/` 直下）には次に実行するための正本を残す** — frontmatterの`status`とプラン間の`order`/`depends_on`/`blocks`、overviewの実装ステータス、調査結果の要約、計画通りにいかなかった場合の差分サマリ、後続ステップ・後続タスクへ反映した実行内容
- **詳細は `progress/` 配下にまとめる** — 生の調査データ、実装中の判断のフル文脈、差分が発生した理由の詳細、完了時の検証記録

## 何をどこに書くか

| 情報                                                          | プランファイル本体                                | progress/ |
| ------------------------------------------------------------- | ------------------------------------------------- | --------- |
| ステップの完了状態                                            | frontmatterの`status`・overviewのチェックボックス | —         |
| プラン間の依存関係・着手条件                                  | overviewの`order`/`depends_on`/`blocks`           | —         |
| 調査結果の要約（後続ステップが前提にする事実）                | 数行の箇条書き + リンク                           | —         |
| 調査の生データ（APIレスポンス例・比較表・読んだページの抜粋） | —                                                 | 記録する  |
| 計画通りにいかなかった変更のサマリ                            | 1〜2行 + リンク                                   | —         |
| 上記変更の理由・背景の詳細                                    | —                                                 | 記録する  |
| 実装中にその場で決めた細かい判断                              | —                                                 | 記録する  |
| 後続ステップ／後続タスクへの実行内容                          | 対象プランを直接更新                              | —         |

「次に何をするか」はプランファイル本体を正本にし、「なぜ変更したか・実装時に何が分かったか」の詳細をprogressにまとめる、という棲み分け。

## progress ファイルの命名

- `{ステップ番号2桁}-{短いスラッグ}.md` — 例: `01-research-results.md` / `02-implementation-notes.md`
- ステップに紐付かない横断的な内容（複数ステップにまたがる手戻りや、プラン終了時の完了記録）は `99-{スラッグ}.md`。完了記録には `99-completion.md` を使ってよい
- 1ステップの実行で詳細が複数の観点に分かれるなら、`02-implementation-notes.md` / `02-error-handling-decision.md` のようにステップ番号で揃えて複数ファイルに分けてよい。1ファイルに無理に詰め込まない

## いつ progress ファイルを作るか

- プランファイル本体の節に「これ以上書くと3〜4行を超えて埋もれる」と感じた瞬間が作成タイミング
- 逆に、1〜2行で済む調査結果や差分は progress ファイルを作らずプランファイル本体に直接書いてよい。ただしプラン完了前には、最終ステップの記録または `99-completion.md` を必ず作り、完了範囲・検証結果・差分の有無を残す
- 目安は「プランファイル本体の1節が、本来の5要素（やること／読むべきファイル／触るファイル／決定事項／ルール更新）以外のメモで埋まり始めたら分離」

## snapshot/ との棲み分け

`snapshot/` は初版プランの逐語コピー（AS-IS、編集禁止）で、progress は実行中に生じた詳細を残す場所。役割が違うため、初版の内容を progress に書き写す必要はない:

- **初版そのもの**: `snapshot/`（[../../README.md](../../README.md) の「初版プランのスナップショット」節）。取得後は編集しない。
- **初版から何を変えたか（要約）**: 親フォルダ側プランの「計画との差分」節。
- **その理由・実行時に何が分かったか（詳細）**: `progress/`。

## task-tracker との棲み分け（セッションをまたぐTODO化）

progress は「プラン1件の実行中に生じた詳細」をプランと同じディレクトリ内にまとめるもの。一方で [task-tracker](../../../skills/task-tracker/SKILL.md) スキルは `.claude/tasks/<task-name>/CURRENT.md` に「今の現状・次にやること」を残し、複数セッションを行き来する際の再開導線にする。両者は別物で、重複させない:

- **1セッションで完結するプラン**: 実行中はprogressもtask-trackerも不要なことが多い。ただし完了前には最終progressを必ず書く（[../03-single-file-example.md](../03-single-file-example.md) 参照）。
- **セッションをまたぐプラン**: プラン本体のfrontmatter `status`・overviewのチェックボックス（ステップ完了）はプラン側、進行中の細かい現状は task-tracker の `CURRENT.md` 側、実行中に生じた詳細（差分の理由・実装メモ）は progress 側、と3層で棲み分ける。後続の作業内容は対象プランを直接更新する。task-tracker の「関連ファイル」節からプラン・progress へリンクを張れば、再開時に一発で辿れる。

## 新規プランを書くとき

progress フォルダは実行開始時点では空でよい（存在しなくてよい）。実行が進んで初めて詳細が溜まったときに作る。テンプレートとしてプランを新規作成するときに progress フォルダを予め作る必要はない。ただし、プラン完了前には必ず最終progressファイルを作る。

## 書き方のポイント

- **progress は「プランファイル本体を読む人が原則読まなくても実装を進められる」ようにする。** 本体を読めば次に進めるようにし、詳細が必要になったときの参照元としてprogressを残す。後続ステップへの事実・作業指示はprogressに列挙せず、対象プランを直接更新する。
- **progress に書くのは「実行してみないと分からなかったこと」に限る。** プラン立案時に既に分かっている決定事項・落とし穴は最初からプランファイル本体の決定事項表に書くべきで、progress に後追いで書くものではない。
- **progress は自由形式でよい。** プランファイル本体のような5要素のフォーマットに縛られない。見出しは「計画との差分／実装メモ／プラン本文への反映」など内容に合わせて自由に立てる。
- **完了時のprogressは必須。** 最終ステップの実行結果に完了範囲・検証結果・差分の有無が揃っていなければ、`99-completion.md`を作る。これを書き終えるまでoverviewを完了にしない。
- **progress はプランファイル本体と一緒にGit管理する。** 実行時の一時メモではなく、次に同じ領域を触る人のための参照記録として残す。ただし調査で叩いた生のAPIレスポンスなど長すぎる生データは要約に留め、本当に必要な抜粋だけを残す。
