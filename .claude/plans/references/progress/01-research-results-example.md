# Step1 調査: 詳細結果メモ（サンプル）

> [../01-research-step-example.md](../01-research-step-example.md) の実行で得られた詳細をまとめたprogressファイルのサンプル。プランファイル本体の「調査結果」節には要約だけを残し、生データ・比較表はここに置く。後続ステップの前提条件は対象プランを直接更新する。実装対象ではありません。

## このファイルの位置づけ

Step1（事前調査）を実行した結果、プランファイル本体に書くには長すぎる詳細が溜まったため、それをここに分離した。プランファイル本体の「調査結果」節は「要約 + このファイルへのリンク」にとどめてある。後続のStep2（実装）は、調査結果を反映済みのStep2プラン本文を前提に進めればよく、**原則このファイルを読み直す必要はない**（詳細が必要になったときの参照元として残す）。

## 調査で読んだページ

- https://zipcloud.ibsnet.co.jp/doc/api — 公式API仕様（エンドポイント・パラメータ・レスポンス）
- https://zipcloud.ibsnet.co.jp/ — レート制限に関する注記（ページ下部の「短時間での大量アクセスはお控えください」）

プランファイル本体にはURLのみを記載し、ページ本文は持ち込まない（[../README.md](../README.md) の「外部知識が必要な場合」節どおり）。

## 生のAPIレスポンス例（成否パターン）

該当あり:

```json
{
  "message": null,
  "results": [
    {
      "address1": "東京都",
      "address2": "千代田区",
      "address3": "千代田",
      "zipcode": "1000001"
    }
  ],
  "status": 200
}
```

該当なし（HTTP 200 のまま `results` が `null`）:

```json
{ "message": null, "results": null, "status": 200 }
```

→ ステータスコードだけで成否判定すると「該当なし」を誤って成功扱いする。`results` が `null` かどうかで判定する。この事実はプランファイル本体の要約にも1行で載せ、Step2の決定事項表で採用済み。

## 検討したが見送った選択肢

- **日本郵便公式データ（Kenall等の有料API）** — 該当なし時の挙動が明確だが課金が発生する。今回は無料要件のため見送り。将来 zipcloud のレート制限が顕在化したら再検討の候補として残す
- **都度呼び出しではなくクライアント側キャッシュ** — 現状のトラフィックでは不要（YAGNI）。`PostalCodeApiClient` にキャッシュの差し込み口だけIFで開けておくか迷ったが、未実装メソッドを先に作るのは過剰なので見送り

これらの検討はプランファイル本体の決定事項表には「レート制限は自前実装しない」と1行に圧縮してある。理由の全文はここ。

## プラン本文への反映

Step2（[../02-implementation-step-example.md](../02-implementation-step-example.md)）の決定事項・注意点・触るファイルは、調査結果に合わせて以下を反映済み。後続実装の作業指示はこのprogressではなくStep2プラン本文を正とする:

1. エンドポイントは `GET https://zipcloud.ibsnet.co.jp/api/search?zipcode={7桁}`
2. 該当なしは HTTP 200 + `results: null`。`results` のnull判定で成否を判別する

4. `ArticleShare/Services/ExternalApi/` 配下に既存の外部API呼び出し実装は無い（新規ディレクトリごと作成）

## 書き方のポイント

- **progress の冒頭に「このファイルの位置づけ」を1段落置く。** 読む人が「プランファイル本体とどう違う・いつ読むべきか」を迷わないようにするため。
- **生データはそのまま貼るのではなく、判定に使う事実が分かる最小限の抜粋にする。** 上記レスポンス例も「成否判定に使う構造」が分かる字句だけ残している。全文を貼るとノイズになる。
- **後続ステップへの引継ぎをprogressで完結させない。** 判明した事実は対象ステップのプラン本文へ反映し、この節には反映先だけを記録する。これにより、後続実装者はprogressを読まずに正しいプランで作業できる。
